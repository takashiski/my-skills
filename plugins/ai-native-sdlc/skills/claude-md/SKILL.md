# claude-md: CLAUDE.md とスキルの整備(Build の土台)

CLAUDE.md は短く、バージョン管理された、Claude 向けの作業メモ。AI ネイティブ SDLC で最初に整えるべきもの。

## 新規作成

1. `/init` 相当の調査をする: ビルド・テスト・lint のコマンド、ディレクトリ構成、主要な技術スタック、規約
2. 草案を書き、**削る**。目安は 1 ページ以内(〜60 行程度)
3. 次の 4 セクションに絞る:

```markdown
# <プロジェクト名>

## コマンド
- ビルド: `...`
- テスト(全体 / 単体): `...`
- lint / format: `...`

## 規約
- <コードを読めば分かることは書かない。読んでも分からない決めごとだけ>

## アーキテクチャ
- <主要モジュールと責務、データの流れを数行で>

## Claude がよくやる間違い
- <具体的に。「X をするときは Y ではなく Z を使う」の形>
```

## チューニング(継続運用)

- Claude が同じ間違いを繰り返したら、「よくやる間違い」に 1 行追加する
- PR レビューで**同じ指摘が 2 回**出たら、CLAUDE.md の修正候補にする(`review` スキルと連動)
- 追加するたびに、古くなった行・コードを読めば分かる行を消す。行数を増やし続けない
- 長くなった領域固有の知識は、スキルに切り出す(下記)

## 棚卸しの観点

既存の CLAUDE.md を見直すときは、各行を次で分類して提案する:

- **残す**: コマンド、読んでも分からない規約、実際に起きた間違い
- **消す**: コードやツール設定から自明なこと、一般論(「きれいなコードを書く」等)、古い情報
- **スキルへ移す**: 特定作業でだけ必要な長い手順・知識
- **hook へ移す**: 「絶対に〜しない」系の強制ルール(`guardrails` スキル)

## スキルへの切り出し

組織知(ブランド、セキュリティ方針、API 設計規約、移行手順など)は `.claude/skills/<name>/SKILL.md` に置き、一貫して適用し、中央で更新する。

- frontmatter の `description` に「いつ使うか」を具体的に書く(これで発火が決まる)
- オーナー(ポリシーオーナー)を決め、変更はその人が承認する
- **スキルは助言であって強制ではない**。常に守られなければならないポリシーは、hook か PR 時チェックで裏打ちする

## 測定

- CLAUDE.md の同じ間違いの再発率
- 新メンバーが最初の PR をマージするまでの時間
