# review: REVIEW.md に基づく AI レビュー(Deploy)

人間が全行をレビューする代わりに、Claude が全 PR をポリシーに沿ってレビューし、人間は重要なコードに集中する。**AI の指摘は PR を承認しない。承認はコードオーナーが行う。**

## モード A: REVIEW.md を作る / 調整する

リポジトリに `REVIEW.md` が無ければ、[references/review-template.md](references/review-template.md) をもとに作る。

1. リポジトリの性質(ドメイン、扱うデータ、規制、既存の CI チェック)を調べる
2. 「Important」の定義を具体的に決める(マージを止めるべきもの)
3. nit の定義と、**1 PR あたりの nit 上限**(例: 3 件)を決める
4. 人間レビュー必須の領域(認証、課金、個人情報、インフラ等)をパスで列挙する
5. テックリードの承認を得てコミット

月次で見直す: 指摘の重要度付けが妥当だったか、nit が多すぎないか。

## モード B: PR / diff をレビューする

1. `REVIEW.md` を読む(無ければテンプレートの既定値で進め、作成を提案する)
2. 対応する `spec.md` / `plan.md` があれば読む
3. diff を **パスごとに** 見る:
   - **バグパス**: ロジック誤り、境界条件、エラー処理、並行性、既存挙動の破壊
   - **セキュリティパス**: 入力検証、認可、秘密情報、インジェクション、依存の追加
   - **コンプライアンスパス**: REVIEW.md / 組織スキルに書かれたポリシーへの適合
   - **仕様パス**: spec の受け入れ条件との整合(spec がある場合)
4. 指摘を Important / nit に分類し、nit は上限までに絞る
5. 人間レビュー必須領域に触れていれば、冒頭で明示する

出力形式:

```
## サマリー
<変更の要約 2〜3 文。人間レビュー必須領域に触れているか>

## Important
1. <ファイル:行> <問題> — <なぜ問題か> — <修正案>

## Nit(最大 N 件)
- ...

## 確認できなかったこと
- ...
```

GitHub 連携がある場合、`@claude` とタグ付けされたレビューコメントには、修正コミットまたは返信で対応する。

## フィードバックを CLAUDE.md に還元する

- **同じ種類の指摘が 2 回出たら**、CLAUDE.md の「よくやる間違い」への追加を提案する(`claude-md` スキル)
- 必ず守らせたいものなら、hook / CI チェック化を提案する(`guardrails` スキル)

## 測定

- 最初のレビューまでの時間
- 人間の手直しなしで解決したコメントの割合
- DORA 指標(デプロイ頻度、リードタイム、変更失敗率、復旧時間)
