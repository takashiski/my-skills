# intent: 意図を intent.md として捕捉する(Plan)

要件を委員会で集めるのではなく、**発案者本人**が Claude と壁打ちして、その場で markdown のプロト仕様にする。プロダクトオーナーがレビューしてからコミットする。

## 手順

1. **問題を聞く**: 誰が・どんな状況で・何に困っているか。解決策ではなく問題から入る。
   - 発案者が解決策から話し始めたら、その背景にある問題を一度言語化して確認する
2. **具体化するまで壁打ち**: 以下が埋まるまで質問と提案を往復する。一度に聞くのは 1〜3 問まで。
   - 対象ユーザーと利用シーン(ユースケース)
   - 現状と、なぜ今それが問題なのか
   - 成功の状態(観測可能な形で)
   - スコープ外にするもの
   - 制約(期限、既存システム、法規・セキュリティ)
   - 未解決の問い
3. **intent.md を生成**: [references/intent-template.md](references/intent-template.md) に沿って書く。リポジトリに組織独自のテンプレート(例: `intent/TEMPLATE.md`)があればそちらを優先する。
4. **発案者に修正してもらう**: 生成物をそのまま確定させない。違和感のある箇所、言い過ぎ・言い足りない箇所を発案者に直させる。
5. **コミット先を決める**: 共有の置き場(多くはプロダクトリポジトリの `intent/` フォルダ)に `intent/<YYYYMMDD>-<slug>.md` として置き、PR を作るかコミット手順を提示する。

## 書き方のルール

- 解決策の詳細(画面設計、API、DB)は書かない。それは `spec` の仕事
- 「速く」「使いやすく」のような曖昧語は、観測可能な基準に言い換える
- 分からないことは推測で埋めず「未解決の問い」に残す
- 1 intent = 1 つの問題。複数に分かれるなら分割を提案する

## ガバナンス

- 作者・日時・改訂は git 履歴で残る。別途の議事録は不要
- 採否の決定は「マージ」または「PR のクローズ」で表す。クローズ時は理由をコメントに残す

## 運用起点の intent

`maintain` スキルの検知結果や、インシデント・セキュリティ検出から intent を作る場合は、「背景」に検知の根拠(メトリクス、閾値、ログ、検出 ID)を記載し、`source: detector` などの出自をメタデータに残す。

## 測定

- 先行: 最初の会話から intent コミットまでの時間
- 遅行: Design に進んだ intent の割合、spec 化後の intent 修正回数
