# AI ネイティブ SDLC プレイブック

出典: [The AI-Native SDLC Playbook](https://claude.com/ja/resources/articles/the-ai-native-sdlc-playbook) を要約・再構成したもの。

## 前提となる問題

コードを書く速度はエージェントで桁違いに上がったが、周辺プロセス(承認ゲート、レビュー、引き継ぎ、ポリシー)は人間の速度のまま。その結果:

- ボトルネックが「計画・レビュー/テスト・デプロイ」へ移る
- 1 行ずつの人間レビューがスケールしなくなる
- 例外が定例の委員会待ちになり、ガバナンスコストが膨らむ

対策は、人間をループに残したまま、エージェントができることを前提にプロセスを組み直すこと。**判断を要する決定の責任は常に人間が持つ。**

## 核となる考え方: 成果物でつながるループ

線形プロセスではなくループにする。各ステージは次のステージが読む成果物をバージョン管理にコミットし、自動で引き継ぐ。git 履歴がそのまま監査証跡になる。

```
intent.md ─▶ spec.md ─▶ plan.md ─▶ diff + tests ─▶ PR(レビュー指摘) ─▶ 本番
    ▲                                                                   │
    └──────────── インシデント / 検知結果を新しい intent.md として書き戻す ◀─┘
```

| ステージ | 従来 | AI ネイティブ | 担当スキル |
| --- | --- | --- | --- |
| Plan | 委員会で要件収集 | 発案者から直接 intent を捕捉 | `intent` |
| Design | アナリストが仕様化 | スキルに導かれた 1 セッションで spec 化 | `spec` |
| Build | 手書きのコードとドキュメント | plan mode → 生成コード、版管理された CLAUDE.md とスキル | `plan`, `claude-md`, `guardrails` |
| Test | ステージ境界の QA ゲート | 自己検証ループと継続的 eval | `verify-loop` |
| Deploy | 人間の逐行レビュー | 多層のエージェントレビュー。人間は重要コードのみ、ゲートは hooks | `review`, `guardrails` |
| Maintain | 人間が本番を監視 | エージェントが監視し、逸脱を新しい intent として書き戻す | `maintain` |

## 導入順序(ステージ順ではなく依存順)

導入はステージの並び順ではなく、依存関係の順に行う。おすすめの順序:

1. **CLAUDE.md**(`claude-md`)— 全ての土台。最も安く効果が大きい
2. **plan mode → plan.md**(`plan`)— 個人の作業から始められる
3. **自己検証ループ**(`verify-loop`)— `make test` 相当の単一コマンドを用意
4. **REVIEW.md による AI レビュー**(`review`)
5. **hooks / settings によるガードレール**(`guardrails`)— ここまで揃うと auto mode を検討できる
6. **intent.md / spec.md**(`intent`, `spec`)— 上流を巻き込む
7. **継続的 eval、並列セッション、CI/CD 連携**
8. **検知 → intent の自動ループ**(`maintain`)

## 現状診断の進め方

ユーザーから「導入したい」「どこから?」と聞かれたら:

1. リポジトリを読み、以下の有無を確認する: `CLAUDE.md`、`.claude/skills/`、`.claude/agents/`、`.claude/settings.json` の hooks、単一コマンドのテスト実行手段、CI 設定、`REVIEW.md`、`intent/` や仕様置き場
2. 上の導入順序に照らして、**最初に欠けているもの**を 1〜2 個だけ提案する(全部一度にやらせない)
3. 該当する個別スキルを使って、その成果物を実際に作るところまで進める
4. 測定指標(下記)のうち、そのステップに対応するものを 1 つ提示する

## ロールの変化

- **発案者(非エンジニア含む)**: Claude と壁打ちして intent を作る。正式な仕様は書かない
- **プロダクトオーナー**: intent をレビュー・修正し、spec をレビューし、懸念をポリシーオーナーと解決する
- **エンジニア**: コードを書く人から、計画し、並列セッションを操縦し、成果物をレビューする人へ
- **テックリード**: REVIEW.md を書き、人間レビューの閾値を決め、レビュー設定を調整する
- **プラットフォームエンジニア**: hooks、managed settings、eval、CI 連携を整える
- **ポリシーオーナー**: スキルを所有し、ポリシー変更を承認する
- **サービスオーナー / オンコール**: 検知結果をトリアージし、変更を承認する

## 各プレイの構成と指標

各プレイは「何が変わるか / 前提とインフラ / 実行手順 / ガバナンス / 先行指標・遅行指標」で考える。代表的な指標:

- Plan: 最初の会話から intent コミットまでの時間 / Design に採用された intent の割合
- Design: intent コミット → spec コミットの時間 / Build 開始後の spec 修正回数
- Build: 初回マージ率、plan → マージ時間、手戻り回数、CLAUDE.md の同じ間違いの再発率
- Test: CI 初回成功率、変更失敗率、eval 合格率、インシデント → eval 化までの時間
- Deploy: 最初のレビューまでの時間、人間の手直しなしで解決したコメント割合、ゲート待ち時間、DORA
- Maintain: 逸脱 → intent までの時間、検出がマージ済み修正になった割合、インシデント再発率

## 原則(迷ったらここに戻る)

- 成果物は必ずリポジトリにコミットし、次のステージはそれを読む
- スキルは助言にすぎない。必ず守るべきポリシーは hook か PR 時チェックで強制する
- エージェントは本番ゲートの手前までは動いてよいが、ゲートは越えない
- 並列化はレビューが追いつく範囲まで
- 導入は小さく始め、まず手で回し、次にスラッシュコマンド化し、最後に自動化する
