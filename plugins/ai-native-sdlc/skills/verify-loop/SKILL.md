# verify-loop: 自己検証と継続的 eval(Test)

QA をステージ境界のゲートにするのではなく、Claude に**自分の作業を検証する手段**を渡し、レビュー前に自分で誤りを直させる。

## 1. 単一コマンドのフィードバックループ

- テスト、ビルド、型チェック、lint を **1 コマンド** にまとめる(例: `make test`、`npm run check`)
- そのコマンドを `CLAUDE.md` の「コマンド」に書く
- 作業の最後に必ず実行し、失敗したら直してから報告する

まだ無い場合は、`package.json` の scripts や Makefile に追加する提案から始める。

## 2. バグ修正はテスト先行

1. 再現する**失敗するテスト**を書く
2. 失敗することを確認して、そのテストだけを先にコミットする
3. **テストを編集せずに**、テストが通るよう実装を直す
4. 必要なら hook でバグ修正中のテストファイル編集をブロックする(`guardrails` スキル)

テストを書き換えて通したくなったら、それは仕様の誤解かテストの誤りのどちらか。止まってユーザーに確認する。

## 3. UI はモックと見比べる

- ブラウザ操作やスクリーンショットのツールを使い、実装画面とモック/デザインを比較する
- 差分を列挙して直す、を **2〜3 往復** するのが目安
- 比較したスクリーンショットは PR に添付できる形で残す

## 4. 検証サブエージェント

作業の最後に、**コードを書いた文脈を持たない新しいコンテキスト**で検証させる。書いたときの思い込みに判定が引きずられないため。

- このプラグインの `verifier` エージェントを使う(spec / plan と diff を渡す)
- 注意: 上のフィードバックループで十分カバーできているなら、検証役を重ねる必要はない。コストに見合うのは、受け入れ条件が多い・テストで表現しにくい変更のとき

## 5. CI での継続的 eval

CLAUDE.md、スキル、hooks を変えたときに「良くなったか」を測る仕組み。

1. 過去の実タスクから、**受け入れられた結果がある 20〜50 件** を集める
2. それぞれを eval(入力となる指示 + 合否判定方法)として書く
3. 定期実行に加え、`CLAUDE.md` / `.claude/skills/` / hooks の変更時に CI で実行する
4. **合格率が下がる設定変更はマージしない**(ゲートにする)
5. 本番インシデントが起きるたびに、それを eval に 1 件追加する

## 進め方

ユーザーの依頼に応じて、1〜5 のうち該当するものを選び、実際にコマンドやテスト、設定を作るところまでやる。まだ何も無いリポジトリなら 1 から始める。

## 測定

- CI 初回成功率、レビュー時間、変更失敗率
- eval 合格率、インシデント → eval 化までの時間
