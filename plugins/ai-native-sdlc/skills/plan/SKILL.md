# plan: plan mode から plan.md へ(Build)

エンジニアは plan mode(Claude はコードを読むだけで編集しない)から始める。**計画が承認されるまでファイルは編集しない。**

## 手順

1. **入力を読む**: `spec.md`(なければ issue / intent / ユーザーの説明)と関連コード、`CLAUDE.md` を読む
2. **調査**: 影響範囲のファイル、既存のパターン、テストの場所、似た実装を特定する。この段階では編集しない
3. **plan.md の草案**: [references/plan-template.md](references/plan-template.md) に沿って書く
4. **反復**: ユーザーと計画を詰める。合格基準は「**このリポジトリを知らない別のエンジニア(または別セッション)が plan.md だけを読んで実装できるか**」
   - 「適宜」「必要に応じて」などの曖昧な指示が残っていたら潰す
   - 変更ファイルごとに何をするかが書かれているか
   - 検証方法(どのコマンドで何を確認するか)が書かれているか
5. **承認とコミット**: ユーザーの承認を得たら `plan.md`(例: `intent/<id>/plan.md` または `plans/<slug>.md`)としてコミットし、そこで初めて実装に入る

## 並列化の判断

plan の中で、互いに独立したタスクを洗い出す。独立性が高ければ:

- 各タスクを別の git worktree + 別セッションで並列実行できる
- 繰り返し発生する作業(検証、移行、ドキュメント更新)は `.claude/agents/` のサブエージェントに任せる
- **最初は 2〜3 セッションまで**。レビューが追いつく間だけ増やす

## auto mode に移る条件

ルーチン作業を編集ごとの承認なしで走らせてよいのは、次が揃ってから:

- [ ] CLAUDE.md がチューニングされている(`claude-md` スキル)
- [ ] 守るべきポリシーがスキルと hook で表現されている(`guardrails` スキル)
- [ ] 単一コマンドで回るテストスイートがある(`verify-loop` スキル)

auto mode ではレビューの対象が「個々の編集」から「長い自律実行の後の成果物(diff、テスト結果、plan との差分)」に移る。

## レガシーシステムとの関係

チケット管理(Jira、ServiceNow 等)が別にある場合、成果物ごとに**唯一の正**を決める:

- リポジトリを正にする(推奨)
- 既存ツールを正にし、MCP で書き戻す
- 最低限、相互にリンクを張る

## 測定

- plan → マージまでの時間、初回マージ率、手戻り回数
- エンジニアあたりの同時セッション数
