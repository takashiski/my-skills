# spec: intent.md から spec.md へ(Design)

アナリストが仕様書を書く代わりに、組織のスキル(ブランド、セキュリティ、コンプライアンス、UX)に制約された 1 セッションで、承認済み intent を spec にする。懸念は隠さずフラグとして明示する。**進めるかどうかは人間が決める。**

## 入力の確認

1. 対象の `intent.md` を読む。`status: accepted` でなければ、その旨を伝えて続行するか確認する
2. 適用すべき組織スキル・ポリシーを探す: `.claude/skills/` 配下、`docs/policy/`、`CLAUDE.md` の記載。見つかったものを列挙し、spec 冒頭の「適用したポリシー」に記録する
3. 関連する既存コード・既存仕様を読み、既存の振る舞いとの差分を把握する

## spec.md の生成

[references/spec-template.md](references/spec-template.md) に沿って書く。要点:

- intent の「成功の状態」を、検証可能な受け入れ条件に分解する(Given / When / Then など)
- ユースケースごとに正常系と主要な異常系を書く
- 外部から見える振る舞い(画面、API、通知、データ)を定義し、内部実装には踏み込まない(それは `plan` の仕事)
- intent に無い要件を勝手に足さない。必要だと思ったら「提案」として分けて書く

## 懸念のフラグ

ポリシー観点ごとに確認し、引っかかるものは spec 内の「懸念」セクションに以下の形式で残す:

```
- [ ] [security|compliance|ux|brand|data|ops] <懸念の内容>
  - 根拠: <どのポリシー / スキル / 既存仕様に照らしてか>
  - 解決に必要な判断者: <ポリシーオーナー / PO / 法務 など>
  - 提案: <Claude の推奨案(あれば)>
```

懸念が解決されるまで spec の `status` は `review` のままにする。

## 段階的な自動化

1. **まず手で回す**: このスキルを使って対話で spec を作り、PO がレビューする
2. **スラッシュコマンド化**: 手順が安定したら、プロジェクトの `.claude/commands/` に「intent パス → spec.md 生成」のコマンドとして固定する
3. **自動化**: intent のマージをトリガーに、CI(GitHub Actions + Claude Code 等)で spec を生成し PR として出す

## レビューとコミット

- PO が spec をレビューし、懸念をポリシーオーナーと解決する
- `spec.md` は対応する `intent.md` の隣にコミットする(例: `intent/<id>/intent.md` と `intent/<id>/spec.md`、またはファイル名で対応づけ)
- 先に進めるかの判断は人間がマージで示す

## フロントエンド

画面を伴う場合、PO がデザインツール(Claude Design など)でプロトタイプを作り、それを spec の参照として添付、または Claude Code に持ち込んで実装の起点にしてよい。

## ガバナンス

spec の冒頭に、使った intent のコミット、適用したスキル/ポリシーとそのバージョン(またはコミット)を記録する。

## 測定

- 先行: intent コミット → spec コミットの時間
- 遅行: Build 開始後に spec が修正された回数
