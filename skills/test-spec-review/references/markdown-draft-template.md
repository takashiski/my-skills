# テスト仕様書事前レビュー用Markdownテンプレート

Excelに起こす前にこの形式で書く。

## 1. 対象不具合の定義

### 1.1 観測された挙動
- 何が起きたか
- どこで起きたか
- 何が見えておかしかったか

### 1.2 再現条件
- 対象画面、または対象機能
- 前提条件
- 入力データ
- 選択値、または状態
- 再現手順

### 1.3 期待挙動
- 本来どうあるべきか
- その根拠

### 1.4 未解決事項
- まだ不明なこと
- 誰に確認すべきか

## 2. 修正方針の前提

- 現時点での不具合理解
- テスト整理に使っている前提
- まだ仮説であり、確定していないこと

## 3. テスト軸

- 対象機能
- 入力条件の軸
- 状態の軸
- 件数、数量の軸
- 例外条件の軸

## 3.1 軸ごとのケース整理と採用理由

各軸について、どのようにケースを分けるかと、その理由を書く。

- 数値条件の場合:
  - 同値分割をどう切るか
  - 境界値をどこに置くか
  - それぞれのケースをなぜ別クラスとして扱うか
  - 代表値を何にするか
  - その代表値で何を確認できるか
- 選択肢条件の場合:
  - 全件確認するのか
  - 同値としてまとめる選択肢があるのか
  - 代表値を何にするか
  - なぜその選択肢群を同値として扱えるのか
  - 代表値で何を確認できるか

例:

- 数量軸
  - 0: ゼロ件として別クラス
  - 1: 恒等値として別クラス
  - 2以上: 増加領域として別クラス
  - 理由: 1は数量乗算漏れを隠し得るため、2以上の代表にはならない
- 選択肢軸
  - A: 単独で確認
  - B,C,D: 同値としてまとめ、代表値はB
  - 理由: B,C,Dは同一分岐を通り、期待結果も同じため

## 7. 検証再現性確認

- 第三者が同じ画面、機能に到達できるか
- 第三者が同じデータ、状態を準備できるか
- 第三者が追加質問なしで同じ手順を実施できるか
- 第三者が観測挙動と期待挙動を区別できるか

## 8. Excel化前チェック

- 不具合定義が安定している
- 再現条件に再現性がある
- 期待挙動に明示的な根拠がある
- 軸ごとのケース整理と採用理由が書かれている
- 全体候補と今回対象が分離されている
- 対象外理由が書かれている
- 未解決事項が明示されている
